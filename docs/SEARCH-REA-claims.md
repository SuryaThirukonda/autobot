## Client-search protocol and background transport (Jobright Autofill 1.24.1: ~api/autofill-client-search, ~api/env-resolver, background message resolveAutofillClientSearchStep)

Jobright's "client search" is a multi-round protocol between an ATS-specific content-script driver, the background service worker, and Jobright's Swan API. The API decides what to type into a site's own search box, and the content script reports back which options the site showed. A site driver builds a start request {source, field_type, question, original_answer}. It sends the request with sendToBackground({name:"resolveAutofillClientSearchStep", body}). The background router (background.js 573-575) hands it to module gQ638. That module normalizes the request, does a no-op chrome.cookies.getAll warm-up for https://jobright.ai, then POSTs JSON to https://api.jobright.ai/swan/autofill/autofill-option-resolve/client-search-step with credentials:"include" and no auth header. The server replies inside an envelope {success:true, result} with one of four actions. REQUEST_SEARCH gives a session id, a fresh round id and a search_input of at most 256 characters. SELECT_OPTIONS picks exactly one value from the options in the current round. RETURN_EMPTY is allowed on a start request only for school. RETRYABLE_FAILURE can carry one of 8 failure codes, a lowercase UUID diagnostic id and retry_after_ms of at most 60000. Continuation requests carry only {resolve_session_id, round_id, options (at most 25: candidate_key ≤128, value ≤256, text ≤512, optional domain ≤256)}. So the server has to keep the session state (source, field, answer, the search it issued) keyed by resolve_session_id. Every object is checked strictly: plain objects only, no unknown or symbol keys, data properties only, non-empty strings with length caps. The background validates the server's result twice (once inside fetch, once in the handler). Any thrown error becomes a bare {action:"RETRYABLE_FAILURE"}, after a console.warn that sorts it as validation, http, response-parse or transport. No site reads retry_after_ms, failure_code or diagnostic_id, so the client treats a retryable failure as final. Site drivers add their own limits: at most 5 searches, the same session id throughout, and no repeated search_input or round_id. The failure-code names (MODEL_*, SESSION_*) suggest the server is a stateful, LLM-backed resolver, but server behaviour cannot be determined statically beyond what the client contract forces. **Flow**

1. Site driver (e.g. iCIMS/Phenom/Kula/RippleHire/OracleCloud/Avature/Jacobs/SmartRecruiters) classifies a field and builds a start request {source, field_type, question:getAutofillClientSearchQuestion(field_type), original_answer} from profile data.
2. Driver calls deps.requestStep(req) -> @plasmohq/messaging sendToBackground -> chrome.runtime.sendMessage(extensionId ?? null, {name:'resolveAutofillClientSearchStep', body:req}).
3. Background chrome.runtime.onMessage router switches on e.name, calls gQ638.default({...e, sender}, {send: sendResponse}) and returns true to keep the channel open.
4. Handler l(e,t) calls i(e.body): normalizeAutofillClientSearchStepRequest(body) runs first, OUTSIDE the try (start vs continuation decided by own key 'source').
5. Inside try: ensureSession() = chrome.cookies.getAll({url:'https://jobright.ai'}, ()=>resolve()) with the result thrown away.
6. fetchAutofillClientSearchStep(normalized) re-normalizes, then POSTs JSON.stringify(normalized) to https://api.jobright.ai/swan/autofill/autofill-option-resolve/client-search-step with credentials:'include', accept '*/*', cache-control 'no-cache', Content-Type 'application/json'. There is no timeout or AbortSignal.
7. A non-2xx response throws 'Failed to resolve autofill client-search step: <status> <statusText>'. A JSON parse failure throws 'Failed to parse autofill client-search response'. The envelope must be a plain object with own success===true and own result.
8. result is validated against the normalized request (REQUEST_SEARCH / SELECT_OPTIONS / RETURN_EMPTY / RETRYABLE_FAILURE rules) and returned in normalized form.
9. The handler validates that already-normalized result a second time with validateAutofillClientSearchStepResponse(result, normalizedRequest).
10. On any thrown error: console.warn('[AutofillClientSearch] Step request failed', {requestPhase:'start'\|'round', errorKind:'validation'\|'http'\|'response-parse'\|'transport'}), then return the bare {action:'RETRYABLE_FAILURE'}.
11. t.send(result) -> sendResponse -> the content script's requestStep promise resolves with the action object.
12. On REQUEST_SEARCH the driver checks the session id is non-empty and unchanged, the search is not repeated and fewer than 5 searches have run. It then types search_input into the site's own widget, captures up to 25 candidates, and assigns candidate_key values.
13. The driver sends a continuation {resolve_session_id, round_id (taken from the REQUEST_SEARCH), options:[{candidate_key,value,text}]} and the loop continues.
14. On SELECT_OPTIONS the driver maps selected_values[0] back to a captured candidate and commits it in the DOM. On RETURN_EMPTY or RETRYABLE_FAILURE it stops with a fallback (iCIMS school: choose 'Other' and fill the companion input).

## iCIMS education client-search driver and widget (Jobright Autofill 1.24.1): contents/sites/icims/education-client-search.js + client-search-widget.js + resolve-tracking.js, with the education loop in contents/sites/icims/index.js and the MAIN-world handlers in background.js

iCIMS School and Major fields are server-driven searches. A field qualifies only when it is a native SELECT rule, its normalized label is in a fixed school or major set, the select carries icimsdropdown-enabled/search/ajax="1", and it has an iCIMS trigger (next sibling with an id) whose `<trigger.id>_ctnr` element has the class dropdown-container. The original_answer is rawSchool for school; for major it is rawMajor, then rawDegree, skipping "other"/"others". The driver then loops on resolveAutofillClientSearchStep. It sends a start payload first, then {resolve_session_id, round_id, options}, and allows at most 5 searches. It rejects a missing or changed session id and any repeated (normalized) search input. The live build does not type to get candidates: captureIcimsProfileOptionsCandidates asks the background to run a MAIN-world same-origin GET to the iCIMS page's own /jobs/profileoptions endpoint (size=25, 3 s abort) in the sender's frame, and both sides validate the result strictly. Each capture produces a "generation" object. It carries a per-select WeakMap token and capture-phase listeners, and any trusted user event (keydown/input/change/click/pointerdown/pointerup) on the select, trigger, container or input invalidates it. That makes the field result "trusted-invalidation". To commit, the driver reopens the dropdown and retypes the search one character at a time with synthetic events. It waits up to 5 s for exactly one visible li whose text matches, then calls ICIMS.dropdowns[id].optionSelected in the MAIN world, falls back to a synthetic click, and accepts only when the native select and the fakeSelected text both match within 500 ms. If a school field fails for any non-invalidation reason, the driver searches "Other", commits the single exact "Other" option, finds a single visible "other school" text input in a sibling row of the same data-collection/data-index, fills it with the raw answer and checks it stays stable for 50 ms within 500 ms. If a major field fails, the select is reset to its placeholder and verified. Every outcome goes into a ledger, which resolve-tracking turns into a resolveTrace.education payload attached to the submit/continue answer-pair event. A DOM-typing capture path (captureFreshIcimsSearchCandidates, with MutationObserver stability) and a matching DOM commit still ship in the widget, but no module imports them in this build. **Flow**

1. index.js runFieldFillPhase: if answer.education is non-empty, call fillIcimsEducationRows(records, {fillClientSearchField: fillIcimsEducationClientSearchField, clientSearchDeps: B, ...}) and store the returned ledger in this.educationClientSearchLedger.
2. fillIcimsEducationRows: syncEducationSections(n) -> getEducationRules -> clearRuleValues(rules[0..min]) -> for each row, sort the children school first, then major, then the rest.
3. For each child: classifyIcimsEducationClientSearchRule(rule) returns 'school', 'major' or null. Null rules go through the regular operationConfig fill.
4. getIcimsEducationOriginalAnswer(fieldType, record): if it is empty, mark the field 'missed' and do no search; otherwise run fillIcimsEducationClientSearchField inside withSkip.
5. Driver: checkpoint(); re-classify (throws if ineligible); build the start payload {source:'icims', field_type, question, original_answer}.
6. Loop: send the start payload, or {resolve_session_id, round_id, options} once both are known, via deps.requestStep -> sendToBackground('resolveAutofillClientSearchStep'). The background normalizes the request, POSTs to API_DOMAIN/swan/autofill/autofill-option-resolve/client-search-step, validates the reply, and turns any error into {action:'RETRYABLE_FAILURE'}.
7. After every step: if the current generation is invalidated, return trusted-invalidation. Push the action onto actions[].
8. REQUEST_SEARCH: check the session id is present and unchanged; reject if 5 searches are already done or the normalized search_input repeats; call captureCandidates(select, search_input).
9. captureIcimsProfileOptionsCandidates: bump the per-select token, resolve trigger, container and inner input, create the generation and attach trusted-event listeners, then sendToBackground('searchIcimsProfileOptions', {selectId, searchInput}).
10. Background: chrome.scripting.executeScript in world MAIN in the sender's tab and frame. It checks for https, an icims.com host, the select id suffix, the hash attribute and the icimsdropdown-* attributes, then GETs /jobs/profileoptions?in_iframe=1&q=&page=0&size=25&parentValue=&id=CandProfileFields.School\|Major&hash= with a 3 s abort. It validates {total, options} and returns {status:'ready'\|'no-results', candidates} or {status:'failure', reason}.
11. Content side: if the token changed or the generation is invalidated, return 'invalidated'. Re-validate the candidates (at most 25, exactly the keys value/text, length limits, dedupe) and check that the status agrees with the count. Return {status, generation}.
12. Driver: hold the new generation and discard the previous one. Fail on a non-ready/no-results status. Slice to 25 candidates and build options [{candidate_key:'candidate-N', value, text}]. Record the round {round_id, search_input, options} and the trace {searchInput, candidateCount}. Continue the loop.
13. SELECT_OPTIONS / SELECT_OPTION: find the selected option (by exact text across all rounds, newest round first, or by round_id+candidate_key). Reject ambiguous text and missing candidates. Reuse the held generation if it belongs to the same round; otherwise recapture with that round's search_input and check the candidate is present.
14. commitExactIcimsProfileOptionCandidate: check the generation and that the container is the same element; click the trigger; retype the generation's searchInput char-by-char; wait up to 5 s for exactly one visible li whose text equals the candidate text.
15. Then sendToBackground('selectIcimsProfileOption'): in the MAIN world, ICIMS.dropdowns[id].findWordFromValue(value) -> optionSelected(word), then a readback check. If the status is not 'selected', click the visible li. Poll up to 500 ms for native selectedOptions === candidate AND the fakeSelected/next-sibling text === candidate text.
16. Success: return {success:true, selected:{candidate_key, value, text}}. Failure: candidate-commit-failed, or trusted-invalidation if the generation was invalidated.
17. RETURN_EMPTY -> 'return-empty'; any other action (RETRYABLE_FAILURE) -> 'retryable-failure'.
18. Failure path k(reason): discard the held generation. For a major field, clearIcimsSearchSelectAndVerify (reset to the placeholder, verify within 500 ms) and append ';major-not-blank' if the clear fails. For a school field, run the 'Other' fallback: capture 'Other', commit the single exact 'other' candidate, resolve the companion input, fill it, then check it is stable for 50 ms within 500 ms. Reasons there are '<reason>;school-<step>'; success means success:true with no 'selected'.
19. finally: discard any held generation. index.js records the ledger entry, updates the section row status (filled/missed/skipped), and logs failures as '[AutofillClientSearch] Education field outcome'.
20. On a click of a tracked submit/continue button, IcimsNavigationTrackingController adds buildIcimsClientSearchTrackingData(ledger) -> {resolveTrace:{education:[{recordIndex, school:{...}, major:{...}}]}} to the answer-pair event's extraData.

## Kula, RippleHire and Jacobs client-search drivers (Jobright Autofill 1.24.1 helper-app), compared against the iCIMS driver

All three sites reuse the same server conversation as iCIMS: requestStep -> sendToBackground("resolveAutofillClientSearchStep"), with REQUEST_SEARCH, SELECT_OPTIONS, RETURN_EMPTY and RETRYABLE_FAILURE actions (ev_96020524104577412edb2feccbd1434429c04779dc16e9c7adef5e4887cadefc, ev_9b7f5e1a8ee22699350334e3a5c8303a8d02fa13ac3ec599fe0aed4f1d3f155b). Each site has its own driver loop and DOM adapter, and they are stricter or looser in different places. Kula has three paths. Education (degree and discipline) and Location (the info.address input) run the server loop on Chakra popovers: one native-setter write, a 600 ms wait, then up to 20 polls at 200 ms until two identical snapshots in a row. Kula Company never calls the server. It types the profile company name, reads the options' React-fiber {id, name, domain} in the MAIN world through a background "kulaCompanyDom" executeScript, and commits only an exact local text match. RippleHire Location is the most defensive driver. It handles two surfaces (bootstrap typeahead #indiaLocation and Google Places #currentLocation). It checks every server field and capture field by property descriptor, with length caps, and allows 25 candidates in total across all rounds. Typing is one keydown/setter/InputEvent/keyup burst, and capture waits up to 3000 ms for the menu, then 100 ms for it to settle, polling every 10 ms. A Places commit that does not stick falls back to ArrowDown and Enter. On failure it restores the input's earlier value rather than clearing it. Jacobs Education (school and major on Select2 AutoCompleteField selects) opens Select2, types into .select2-search__field (through jQuery if one is visible, otherwise InputEvent plus 'a' keydown/keyup), waits 1100 ms, then polls 40 times at 100 ms. Its commit re-types the selected text, clicks the li and checks the hidden select's selectedOptions[0]. When a school search comes back RETURN_EMPTY, it picks 'Other' and fills the companion field 2104. By contrast, iCIMS types character by character, uses a 650 ms capture window with 20 ms polls and 3 stable snapshots, accepts SELECT_OPTION (singular), searches every round for the selection and tracks generation invalidation. Of the three new drivers, only Jacobs searches all rounds for the selection. Kula and RippleHire match only within the latest round. Server behaviour (how search_input is chosen, when RETURN_EMPTY is sent) cannot be determined from this client code.

**Flow**

1. BaseFiller site class decides which rules go to client search: Kula wraps the TEXT, SEARCH and SELECT operation handlers (classifyKulaLocationField, classifyKulaEducationField, classifyKulaCompanyField), RippleHire's TEXT handler checks isRipplehireLocationClientSearchRule, and Jacobs' education SELECT handler checks getJacobsEducationClientSearchFieldType.
2. Read the original answer from the profile record (field-specific key lists; RippleHire uses profileData.location city/state/country first). An empty value gives 'missing-original-answer'.
3. Send the first request {source, field_type, question, original_answer} through requestStep -> background resolveAutofillClientSearchStep (not used for Kula Company).
4. On REQUEST_SEARCH: check the round limit (5 searches), check that the session id is stable, reject a repeated round_id or normalized search_input, then call captureCandidates(input, search_input).
5. Capture: write the search text into the input or Select2 search field, wait for the site's debounce (Kula 600 ms, Jacobs 1100 ms, RippleHire polls from the start within 3000 ms), and poll the listbox until it settles (Kula 2 identical snapshots at 200 ms; Jacobs 2 at 100 ms; RippleHire 100 ms settle at 10 ms polls).
6. Turn the rows into options {candidate_key, value, text[, domain]}, at most 25, and send a continuation request {resolve_session_id, round_id, options}.
7. On SELECT_OPTIONS with exactly one selected text: find the single matching option (Kula/RippleHire in the latest round only, Jacobs across all rounds), then call commitCandidate.
8. Commit: click the option (Kula mousedown/mouseup/click; RippleHire pointer and mouse sequence plus a keyboard fallback for Places; Jacobs mousedown/mouseup/click on the Select2 li plus input/change on the select), then read the value back.
9. On failure: Kula clears the input to ''; RippleHire restores the earlier value if the extension owns the current value; Jacobs closes Select2 with an overlay click and, for a school with return-empty, falls back to 'Other' plus the companion input.
10. Report: Kula sets updateMissedProgress for the section, RippleHire logs sanitized telemetry, Jacobs logs [Jacobs][Education] client-search with roundCount and candidateCounts.

## Jobright Autofill 1.24.1 - education client search for Oracle Cloud (school/major LOV), Phenom (school), Avature (institution/major select2) and SmartRecruiters (institution spl-autocomplete)

All four sites run the same server-driven loop. The client sends a start body {source, field_type, question, original_answer} to the background message "resolveAutofillClientSearchStep". The server answers with one of four actions. REQUEST_SEARCH means the site types the server's search_input into the live widget, scrapes up to 25 visible candidates and sends them back with the same resolve_session_id and the new round_id. SELECT_OPTIONS means the site checks that exactly one candidate's text matches, then clicks the real option and confirms it by reading the field back. RETURN_EMPTY and RETRYABLE_FAILURE both end the attempt with no retry: retry_after_ms is checked for format but no code ever reads it. The background handler turns every validation, HTTP, parse or network error into {action:"RETRYABLE_FAILURE"}, and its fetch has no timeout. Only Phenom puts limits on each stage: a frozen table (prepare 5s, probe 12s, wait 5s, clear 2s, resolve 60s) enforced by a stage AbortController that is also tied to the global cancel/skip signals and to a per-field attempt controller. In the client-search path the stage signal is never passed to the work functions, so a timeout only abandons the promise. Oracle, Avature and SmartRecruiters have no AbortController at all and depend on fixed poll loops (for example Oracle 14x250ms, SmartRecruiters 30x100ms, Avature 5000ms windows). Oracle also gathers LOV data. Before typing it asks the background to install a main-world interceptor (it patches fetch, XHR open/send, Array.prototype.filter and a PerformanceObserver; TTL 6000ms) that grabs the hcmRestApi LOV response. It then matches visible dropdown texts one-to-one against LOV items, so each candidate's value is the LOV ContentItemId (school) or LookupCode (major). What happens on RETURN_EMPTY differs by site. Oracle types the raw profile value, except for an educationalestablishmentid school field. Phenom keeps the record as it was, so the generic search fill runs with the original answer. Avature and SmartRecruiters clear the field and mark Education as missed; SmartRecruiters also skips the education Save click. Static analysis is backed by REA evidence ev_9b7f5e1a8ee22699350334e3a5c8303a8d02fa13ac3ec599fe0aed4f1d3f155b (carved slice parsed) and the import trace ev_96020524104577412edb2feccbd1434429c04779dc16e9c7adef5e4887cadefc; the original bundle analysis is ev_136e60682c6df9cd7c0d153f157fc418bee52706ac86da011c7550e95996d489. Server-side selection logic cannot be determined from the client and is marked unknown.

**Flow**

## Local (non-server) option matching and typeahead search in the Jobright Autofill 1.24.1 helper-app

Most option matching in Jobright never touches its server. One shared module, choice-match, cleans up text with NFKC, folds curly quotes, collapses whitespace, trims and lowercases. It then accepts an option only if exactly one option equals the answer. If two or more options match, it returns nothing rather than guessing. About 45 site modules use this exact-unique rule, and the generic dom.js filler adds a small synonym map on top (true→yes, false→no, linkedin→linkedin.com, indeed→indeed.com). Fuzzy scoring is rare and different on each site. Workday alone uses a Levenshtein similarity score (crawler/utils/select fuzzyFindBest), with threshold 0.7 when strict and 0.5 when not, and a tie for best score returns null. Its search cascade goes exact → token → substring → fuzzy, and fuzzy is switched off for skills, school and field-of-study. Ashby uses Fuse.js (threshold 0.35) plus a substring check in both directions, and resolves school names through Ashby's own GraphQL school search with a token-overlap rule (overlap ≥ max(n-1, 2)). Greenhouse react-select tries exact → startsWith → includes, but only exact for school and discipline. Meta tries exact-unique, then for location fields a comma-segment prefix match. Apple, Walmart and the Google skills field accept exact matches only. For typing, each site sets the value through the native value setter, fires input/change (and on some sites key events or one character at a time), then polls for options. Polling uses getTargetOrTimeout (100 ms per step, N retries) or waitForCondition (a MutationObserver with an interval fallback), with a timeout per site, and many sites re-check after clicking that the choice was really committed. The server is used only where the client cannot decide alone. Pinpoint addresses, Meta current location and Workday or Greenhouse education go through a single-shot resolveAutofillOperation call. Education and location fields on avature, icims, jacobs, kula, oraclecloud, phenom, ripplehire and smartrecruiters go through the multi-round client-search-step loop. Even then, the client re-matches the server's chosen value against the live options by exact text and requires exactly one match.

**Flow**

1. The site filler (BaseFiller field handlers) gets the answer value(s) for a field rule; values are usually wrapped into an array of candidates.
2. Native <select>: dom.fillSelectField picks the first option whose text passes answer.isMatched (punctuation stripped, '*' removed, whitespace collapsed, lowercased, then equal). Sites like Greenhouse, Walmart and Apple use their own exact text/value comparison instead.
3. Radio/checkbox groups: dom.fillCheckBoxesField normalizes each answer with normalizeChoiceText and rejects the group (returns false) if more than one option exactly matches. It then calls findExactChoice; if that finds nothing it retries with the synonym map {true:yes,false:no,linkedin:linkedin.com,indeed:indeed.com}.
4. Typeahead/combobox: open the widget (click the trigger, Workday promptIcon/promptSearchButton, a Meta popover button, the Pinpoint bp3 select button), then find the live search input (aria-controls, a scoped container, activeListContainer searchBox, or document.activeElement).
5. Type the query: the native HTMLInputElement value setter, then input/change events. Workday also fires keydown/keyup for the last character plus an Enter keydown/keypress/keyup. Apple types one prefix at a time with beforeinput/input InputEvents at 20 ms (clear step) or 35 ms (each character). Greenhouse clears for 50 ms, sets the value, then waits 300 ms to settle.
6. Wait for options: poll with getTargetOrTimeout (100 ms delay, N retries) or waitForCondition (MutationObserver plus setInterval, with a timeout). Loading and no-options notices are detected; Greenhouse compares option snapshots so stale options are ignored; Workday detects 'No matches found' and scrolls virtualized lists.
7. Match locally: site-specific normalization, then an exact match that must be unique. Some sites then allow wider fallbacks (startsWith, includes, token, comma-segment prefix, Fuse.js, Levenshtein), each gated by field type (school, skills, location).
8. Commit: a synthetic pointer/mouse event sequence on the option (or option.click). Greenhouse and Workday may instead call the React Select instance's setValue/updateStateFromValue through a MAIN-world fiber script. Workday adds an Enter fallback when nothing is committed.
9. Verify the read-back (Greenhouse singleValue or hidden input; Workday selectedItemList menuItem count or button text; Meta button text; Google chips; Pinpoint address1 value), and retry with another candidate string (token prefixes, comma or dash segments, re-sending the query) if needed.
10. On failure: clear the input / press Escape / blur, log a reason string, return false or throw FillError (Ashby).
11. Server paths are used only for specific fields. resolveAutofillOperation is a single call whose result carries action and selected_values. The client-search-step loop (REQUEST_SEARCH → the client captures up to 25 candidates → SELECT_OPTIONS) ends with the client re-matching selected_values[0] by exact text and requiring exactly one match.

## Cancellation, checkpoints, stability waits and tracking around Jobright client-search (Jobright Autofill 1.24.1)

Cancel and Skip are both cooperative. ~contents/methods/cancellation keeps module-global state: the current cancel AbortSignal, the current per-field skip AbortController/signal, and a "pending skip" flag. checkpoint() checks these synchronously and throws CancelledError or SkippedError. cancellableDelay() is a setTimeout that rejects as soon as either signal aborts. withSkip() gives each field its own skip controller and turns any outcome after a skip into a SkippedError. createCancellation(), owned by BaseFiller, makes a new cancel controller for each fillForm run. The sidebar's Stop and Skip buttons send DOM CustomEvents ("CancelAutoFill" / "SkipAutoFill"). Hooks turn these into instance.cancel()/skip() and forward them to iframes with postMessage (CANCEL_AUTO_FILL / SKIP_AUTO_FILL). The Skip button only appears after the same field has been current for 2000 ms. A search step that is already running is not aborted: requestStep is a plain sendToBackground, and the background fetch to /swan/autofill/autofill-option-resolve/client-search-step has no signal and no timeout. The search drivers instead call checkpoint() right before and after every awaited step, capture and commit, so a late reply is thrown away and only pending delays reject at once. Stale candidate lists are thrown out by generation tokens kept per element in WeakMaps. On iCIMS a generation is invalidated by capture-phase listeners that fire on any isTrusted user event (keydown/input/change/click/pointerdown/pointerup), not by a MutationObserver. On RippleHire it is invalidated by losing focus or a changed input value. MutationObservers are used only to see whether the dropdown changed after typing. Results are accepted only after the dropdown stays the same for a while: 3 equal polls 20 ms apart on iCIMS DOM typing, a fingerprint unchanged for 100 ms within 3000–3110 ms on RippleHire, 3 equal polls 200 ms apart after a 600 ms wait on Kula, and an iCIMS companion input whose value holds for 50 ms within 500 ms. Search telemetry that leaves the device is the iCIMS education resolveTrace: rounds with searchInput and candidateCount, actions, the selected value/text, and failureReason, all capped in length. It is attached to the autofill_answer_pair payload when the user clicks submit/continue. UI events (autofill_cancel_click, autofill_skip_click, autofill_skip_exposure) go through trackEvent→postEventSubmit. RippleHire search diagnostics only go to the console. This builds on the recorded evidence ev_9b7f5e1a8ee22699350334e3a5c8303a8d02fa13ac3ec599fe0aed4f1d3f155b (carved search slice) and ev_96020524104577412edb2feccbd1434429c04779dc16e9c7adef5e4887cadefc (import trace into api/autofill-client-search.js).

**Flow**

1. BaseFiller constructor: fillCancel = createCancellation(() => taskQueue.clear(), progressTracker.setCurrentField); this.cancel/this.skip are bound to fillCancel.cancel/skip.
2. fillForm() runs inside fillCancel.wrap(): a new AbortController for the run, the pending-skip flag reset, the field tracker installed, and withCancellation(signal) making the signal global; checkpoint() is called after beginSiteRulesSession.
3. Each field handler (createOperationHandlerFactory) calls updateCurrentField(label), which updates the progress tracker and starts the 2000 ms useSkipTimer, then runs the fill inside withSkip (one AbortController per field).
4. iCIMS education: updateCurrentField('Education'); each school/major field runs inside withSkip(() => fillIcimsEducationClientSearchField(rule, record, rowIndex, deps)).
5. The driver loop calls checkpoint(), then deps.requestStep (sendToBackground 'resolveAutofillClientSearchStep', no AbortSignal), then checkpoint() again and checks S?.invalidated. Background: the cookie session warm-up, then a POST with no timeout; any error becomes {action:'RETRYABLE_FAILURE'}.
6. On REQUEST_SEARCH: round/session/repeat checks, checkpoint(), then captureCandidates. This creates a new generation token and attaches trusted-event invalidation listeners, makes the MAIN-world profileoptions fetch (3 s abort), then checkpoint() and a token/invalidated check. The driver adopts the generation (A), discarding the previous one, keeps candidates[0..25], records the round {searchInput, candidateCount} and continues.
7. On SELECT_OPTIONS/SELECT_OPTION: the driver resolves the candidate, reuses the current generation or recaptures, then commitCandidate. The commit checks the generation, token and container identity, retypes, waits ≤5000 ms for exactly one visible option, selects in the MAIN world or clicks, and waits ≤500 ms for native and visible readback. It then discards the generation and returns success.
8. Any failure goes to k(reason): school falls back to the 'Other' option plus the companion input (50 ms stability check), and major clears the select (clearIcimsSearchSelectAndVerify bumps the generation counter). The outcome {rowIndex, fieldType, actions, rounds, selected\|failureReason} is pushed to the ledger.
9. User clicks Stop: trackEvent autofill_cancel_click, then CustomEvent 'CancelAutoFill', then useRegisterAgentCancel: cancelPreAutofillAccountFlow + instance.cancel() (aborts the run controller and clears the taskQueue) + postMessage CANCEL_AUTO_FILL to iframes. Pending cancellableDelay calls reject with CancelledError at once; awaited messages are thrown away at the next checkpoint(); CancelledError is rethrown through every handler.
10. User clicks Skip (shown only after the field has been current for 2000 ms): trackEvent autofill_skip_click, then CustomEvent 'SkipAutoFill', then instance.skip(): skipCurrentField() aborts the active withSkip controller, or sets a pending flag if none is active. The withSkip boundary turns this into SkippedError; the field is marked skipped/missed, and on iCIMS education every remaining education row is abandoned (break n).
11. RippleHire on Cancel/Skip: if the extension already typed into the input, clearTemporaryValue runs with a 250 ms budget and its own AbortController, and only clears values the extension owns; then the error is rethrown.
12. Telemetry: on a click of a tracked submit/continue button (capture-phase document listener, one AbortController per run), buildIcimsClientSearchTrackingData(ledger) produces {resolveTrace:{education:[...]}}. This goes into extraData of the autofill_answer_pair event and then to sendToBackground 'postAutofillAnswerPairAttributed'.
